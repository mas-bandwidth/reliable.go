# C parity check — 2026-10-14

Go port `mas-bandwidth/reliable.go` at `c0411a7` (branch
`sprint/reliable-go-port`) checked against the C reference
`mas-bandwidth/reliable` at branch `sprint/reliable-audit-fixes`, commit
`c8995dc` (contains the fix stream at and after `7862477e`; the C library is
normative).

Port files read in full: `reliable.go`, `packet_header.go`,
`sequence_buffer.go`, `endpoint.go`, `wire_compat_test.go`,
`interop/regenerate.sh`, `interop/transcript.c`. C files read in full:
`reliable.h`, `reliable.c`. Counter order is identical on both sides (eleven
counters, `reliable.h` `RELIABLE_ENDPOINT_COUNTER_*` vs `reliable.go`
`CounterNum*`).

Verdicts used: `BUG` (the port is wrong and must be fixed), `DIVERGENCE`
(an allowed or structural difference, reason given), `QUESTION` (not enough
information to decide), `MATCH` (the port agrees with C; what was compared is
named).

---

## 1. Wire format

**MATCH.**

Compared `writePacketHeader` (`packet_header.go:11-77`) against
`reliable_write_packet_header` (`reliable.c:892-976`), and
`readPacketHeader` (`packet_header.go:81-167`) against
`reliable_read_packet_header` (`reliable.c:1008-1145`): same prefix-byte bit
assignments (bit 0 fragment flag, bits 1-4 ack_bits byte-present, bit 5
one-byte sequence difference), same little-endian sequence and ack, same
elision rules and same canonical re-encode. `readFragmentHeader`
(`packet_header.go:173-272`) matches `reliable_read_fragment_header`
(`reliable.c:1147-1238`): 5-byte fragment header (prefix 1, sequence,
fragment id, count-1), embedded packet header on fragment 0 only, the
non-canonical-header rejection, and the non-last-fragment size check.
`MaxPacketHeaderBytes = 9` (`reliable.go:58`) equals
`RELIABLE_MAX_PACKET_HEADER_BYTES` (`reliable.h`); `FragmentHeaderBytes = 5`
(`reliable.go:61`) equals `RELIABLE_FRAGMENT_HEADER_BYTES` (`reliable.h`).
Send-path fragmentation layout (`endpoint.go:282-313`) matches
`reliable_endpoint_send_packet` (`reliable.c:955-1005`): fragment 0 carries
the canonical packet header, non-last fragments carry exactly `fragment_size`,
last carries the remainder.

## 2. Sequence buffer

**MATCH.**

`sequence_buffer.go` compared function-by-function against `reliable.c`:
`testInsert` (`sequence_buffer.go:65-67`) vs
`reliable_sequence_buffer_test_insert` (`reliable.c:293-296`);
`insert` (`sequence_buffer.go:69-80`) vs `reliable_sequence_buffer_insert`
(`reliable.c:298-311`); `advance`/`advanceWithCleanup`
(`sequence_buffer.go:82-87,104-109`) vs
`reliable_sequence_buffer_advance_with_cleanup` (`reliable.c:344-352`);
`removeEntries` wrap handling (`sequence_buffer.go:41-61`) vs
`reliable_sequence_buffer_remove_entries` (`reliable.c:263-291`);
`exists`/`find` (`sequence_buffer.go:119-129`) vs
`reliable_sequence_buffer_exists`/`_find` (`reliable.c:363-377`);
`generateAckBits` (`sequence_buffer.go:140-151`) vs
`reliable_sequence_buffer_generate_ack_bits` (`reliable.c:379-393`).
The stale test, wrap, index-by-`sequence % num_entries`, and ack-bit
generation agree. (The power-of-two *size* rule lives in config validation —
item 6 — not in the buffer itself; C's `reliable_sequence_buffer_create`
asserts `num_entries > 0` in debug only, Go panics on `<= 0` in
`newSequenceBuffer` (`sequence_buffer.go:16-19`), which the endpoint already
rejects.)

## 3. Receive path ordering and counters

**MATCH for the regular-packet path; BUG in the fragment path.**

Regular-packet path (`endpoint.go:380-471`) matches
`reliable_endpoint_receive_packet` (`reliable.c:1324-1452`): counters
increment in the same order — `packets_received` before the header read, then
`packets_invalid` (bad header), `too_large_to_receive` (payload), `stale`
(failed `test_insert`), `duplicate` (`exists`), then process callback, insert,
fragment-reassembly advance, and the ack walk. Fragment duplicate / mismatch /
complete handling and the `fragments_received` / `fragments_invalid`
increments (`endpoint.go:472-553`) match `reliable.c:1454-1594`.

**BUG** — the port omits the stale-fragment check against the received window.
C tests `!reliable_sequence_buffer_test_insert(endpoint->received_packets, sequence)` immediately after the `exists` check and counts the fragment
`NUM_FRAGMENTS_INVALID` (`reliable.c:1473-1479`). Go goes straight from the
`receivedPackets.exists(sequence)` check (`endpoint.go:485`) to the
`fragmentReassembly.find` lookup (`endpoint.go:493`) with no `test_insert`.
A fragment behind the received window is therefore accepted into reassembly
(if the reassembly buffer still has room) instead of being counted invalid,
so the two sides disagree on the `num_fragments_invalid` counter and on
whether the fragment is delivered.

## 4. Replay and window semantics

**BUG.**

C moves the received window only when a packet is accepted: the sole
`received_packets` mutation is the `insert` in the accepted-packet path
(`reliable.c:1372-1377`), and the first-fragment path carries the comment
"the received window moves when the reassembled packet is accepted, not here"
(`reliable.c:1496`) with no `received_packets` write. Go calls
`endpoint.receivedPackets.advance(sequence)` on a first fragment
(`endpoint.go:504`), moving the received window before the fragmented packet
is accepted. Consequence: a far-ahead first fragment makes a genuine
subsequent packet (sequence between the old and new window edge) be counted
`num_packets_stale` in Go where C accepts it. The C side also moves
`fragment_reassembly`'s own window on the first fragment (item 9), but never
the received window.

## 5. Malformed input

**MATCH.**

Zero-length receive: `packetBytes == 0` → `num_packets_invalid`
(`endpoint.go:361-367`) vs `packet_bytes <= 0` → `NUM_PACKETS_INVALID`
(`reliable.c:1302-1307`). Oversize: `packetBytes > MaxPacketSize+MaxPacketHeaderBytes+FragmentHeaderBytes` →
`too_large_to_receive` (`endpoint.go:369-376`) vs the identical bound
(`reliable.c:1309-1316`). Truncated headers: `readPacketHeader` returns `-1`
on each too-short shape (`packet_header.go:84,107,117,133`) matching
`reliable_read_packet_header` (`reliable.c:1014,1042,1058,1090`), and
`readFragmentHeader` returns `-1` below `FragmentHeaderBytes`
(`packet_header.go:176-181`). Bad fragment counts: `num_fragments > max_fragments` and `fragment_id >= num_fragments` both return `-1`
(`packet_header.go:201-213`) matching `reliable.c:1185-1204`. All are counted
and ignored; none panics, throws, or reads out of bounds on the receive path
(the index into `fragmentReceived[256]` is bounded by
`fragment_id < num_fragments <= max_fragments <= 256`).

## 6. Config validation and defaults

**Defaults MATCH; three findings.**

Defaults agree: `DefaultConfig` (`endpoint.go:45-62`) vs
`reliable_default_config` (`reliable.c:533-559`) — 16 KiB max packet,
`fragment_above` 1024, 16 fragments of 1024, ack buffer 256, sent/received
256, reassembly 64, rtt smoothing 0.0025, rtt history 512, loss 0.1,
bandwidth 0.1, header 28. The refusal messages/order are near-identical for
the shared checks.

**BUG** — the port does not enforce power-of-two sequence-buffer sizes up to
16384. C `reliable_config_valid` rejects `sent_packets_buffer_size`,
`received_packets_buffer_size` and `fragment_reassembly_buffer_size` that are
not a power of two in `[1,16384]` (`reliable.c:575-585`, applied at
`reliable.c:629-641`). Go `NewEndpoint` only checks `> 0`
(`endpoint.go:140-148`) and then `make`s the buffers
(`endpoint.go:187-189`), so e.g. `SentPacketsBufferSize = 100` is accepted and
the `sequence % num_entries` index collides after a wrap.

**DIVERGENCE** — `fragment_reassembly_byte_budget` is absent from the port.
C carries it in the config (default `256 * 1024`, `reliable.c:554`) and
refuses a negative value (`reliable.c:644-648`). Go `Config`
(`endpoint.go:23-41`) has no such field, so the unfinished-reassembly byte
budget (item 8) cannot be expressed or enforced here.

**DIVERGENCE** — the port's `packet_header_size` upper bound omits the header
allowance. C refuses
`packet_header_size + max_packet_size + 9 + 5 > INT_MAX`
(`reliable.c:692-699`); Go refuses only
`packet_header_size > maxInt - max_packet_size` (`endpoint.go:176-178`),
missing the `+14` (`RELIABLE_MAX_PACKET_HEADER_BYTES + RELIABLE_FRAGMENT_HEADER_BYTES`), so a config near `INT_MAX` is accepted where
C refuses it.

**BUG** — absurd `AckBufferSize`/`RTTHistorySize` panic in `make` where C
refuses. C sizes every allocation with `reliable_checked_size`, refusing a
count whose product does not fit (`reliable.c:118-133`, applied to the ack
buffer and rtt history at `reliable.c:731-737`). Go
`make([]uint16, 0, config.AckBufferSize)` (`endpoint.go:185`) and
`make([]float64, config.RTTHistorySize)` (`endpoint.go:191`) panic on an
out-of-range or unallocatable size instead of returning an error.

## 7. Statistics

**BUG (rtt min, Reset) and DIVERGENCE (float width).**

**BUG** — `rttMin` uses a `10000.0` sentinel where C decides by sample count.
Go seeds `minRTT := 10000.0` (`endpoint.go:597`) and later `if minRTT == 10000.0 { minRTT = 0.0 }` (`endpoint.go:613`). C seeds `FLT_MAX` and chooses
`rtt_min = 0.0f` only when `count == 0` (`reliable.c:1669-1706`, with the
comment "the sample count, not the value of min_rtt, says whether the history
is empty"). A real rtt of exactly 10000 ms therefore reports `rtt_min` 0 in
Go and 10000 in C.

**BUG** — `Reset` does not clear statistics. Go `Reset` (`endpoint.go:571-588`)
clears acks, sequence, counters and the three tracking buffers, but leaves
`rtt`, `rttMin`, `rttMax`, `rttAvg`, the three jitter values, `packetLoss` and
the three bandwidth values unchanged, and does not refill `rttHistoryBuffer`
with -1. C `reliable_endpoint_reset` (`reliable.c:1616-1657`) zeroes every
statistic (`reliable.c:1622-1633`) and refills the rtt history with `-1.0f`
(`reliable.c:1639-1643`), so after `Reset` the getters differ.

**DIVERGENCE** — float width. The port stores and returns `float64`
(`endpoint.go:98-110`, getters `endpoint.go:798-847`); C uses `float`
(`reliable.c:470-484`, getters `reliable.c:1966-2016`). Even on identical
inputs the statistics are not bit-exact; the differential leg below compares
counters and delivery, not the float getters. The remaining statistics logic
(jitter count-based, packet loss, bandwidth smoothing) matches in structure.

## 8. Memory

**MATCH for zeroing and name safety; DIVERGENCE for allocation failure and
the byte budget.**

The reassembly buffer is zeroed on both sides: Go `make([]byte, packetBufferSize)` zeroes (`endpoint.go:510`); C `memset(packet_data, 0, packet_buffer_size)` (`reliable.c:1540`). The config name is safe on both
sides: Go `Config.Name` is a Go `string`; C NUL-terminates its copy in create
(`reliable.c:779`).

**DIVERGENCE** — allocation failure cannot be refused or counted in the port.
C returns `NULL` from `reliable_endpoint_create` on any allocation failure
(`reliable.c:806-815`) and, on the receive path, a `NULL` from
`allocate_function` drops the fragment and counts `NUM_FRAGMENTS_INVALID`
(`reliable.c:1525-1534`). Go has no allocator hook and uses `make`, which
panics on failure; there is no refused-and-counted path.

**DIVERGENCE** — the unfinished-reassembly byte budget is absent. C refuses a
first fragment whose buffer would push unfinished reassemblies past
`fragment_reassembly_byte_budget` (default 256 KiB) and counts it invalid
(`reliable.c:1511-1523`). Go has no budget (item 6) and allocates every
first-fragment buffer unconditionally.

## 9. `fragment_reassembly` advances its own window on a first fragment

**MATCH (both carry the same C follow-up).**

This is a C follow-up the fix stream reports, not yet fixed in C:
`reliable_sequence_buffer_insert_with_cleanup` advances the reassembly
buffer's own `sequence` on a first fragment (`reliable.c:322-326`), so a
far-ahead unfinished fragment can still stale a genuine fragmented packet in
reassembly. The port reproduces the same behaviour in `insertWithCleanup`
(`sequence_buffer.go:89-95`). Compared, they agree; neither side is further
along. Note the *received* window bug is separate (item 4): Go additionally
advances `receivedPackets` on a first fragment, which C never does.

## 10. Interop pin

**DIVERGENCE (pin is not current).**

The port's own interop pin is `RELIABLE_C_COMMIT=d4b6fe0882d2d752d57984f70e7a29037982984f`
= C `v1.4.4` (`interop/regenerate.sh:19`). C has since cut `v1.4.5`
(`e4e70927`), and the audit fix stream
(`sprint/reliable-audit-fixes`) is at `c8995dc` (at and after `7862477e`).
`interop/regenerate.sh` therefore tests against a release that predates the
fix stream this card ports. A card should bump the pin to `v1.4.5` (or the
fix branch) and regenerate `testdata/c_transcript.txt.gz`.

## C reference leg

The differential oracle `interop/fixes_oracle.c` and the test
`fixes_diff_test.go` were written per the card and run against
`RELIABLE_C_DIR` at `c8995dc` (branch `sprint/reliable-audit-fixes`), built
with `cc -O2 -ffp-contract=off -I$RELIABLE_C_DIR`. The command:

    RELIABLE_C_DIR=<checkout> go test -count=1 -run TestCDifferential .

is **red at BASE**: the transcripts diverge at input 6 (and the stale counter
then carries into every later line). First differing line:

    c:  6 accepted num_packets_received 3:4 2 5 2 0 0 0 0 0 1 0 1
    go: 6 refused num_packets_received -  2 5 2 1 0 0 0 0 1 0 1

Inputs 1-5 match; inputs 7-10 (zero-length, oversize, truncated header, bad
fragment count) each produce the same per-input delta, differing only in the
carried-forward `num_packets_stale` value. The divergence is exactly item 4:
the far-ahead first fragment at input 5 advances Go's received window
(`endpoint.go:504`), so the genuine packet at sequence 3 in input 6 is counted
stale in Go where C accepts it. The hostile inputs of item 5 themselves match
C.
